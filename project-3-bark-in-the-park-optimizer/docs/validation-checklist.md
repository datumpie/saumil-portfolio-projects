# Verification & Reproducibility Standard -- Project 3: The Bark in the Park Concession Optimizer

A third party should be able to answer **YES** to all eight questions below.
Here is exactly how, for this project.

| # | Question | How it's satisfied here |
|---|----------|--------------------------|
| 1 | Can they recreate this from documentation alone? | Yes. `README.md`'s "Deployment" section gives copy/paste setup steps requiring only Python and one `pip install` command. |
| 2 | Can they verify the APIs? | N/A for this project -- there is no external API, by design (see Business Problem: real POS data is proprietary, which is exactly why this is a statistical proxy model instead of a live data pull). What takes the place of "API verification" here is distribution-parameter verification, covered in row 5 below. |
| 3 | Can they confirm the DB tables? | Yes. Open `stadium_concessions.db` in any SQLite browser and confirm the two tables `games` (81 rows) and `revenue_detail` (162 rows -- 81 games x 2 revenue categories) exist, matching the schema in `stadium_concessions.py`'s `init_database()` function. |
| 4 | Can they run automated pass/fail tests? | Yes. `pytest tests/test_stadium_concessions.py -v` runs 15 tests covering schedule generation, reproducibility, realism bounds, and full database persistence. Run with: `pip install pytest` then `pytest tests/test_stadium_concessions.py -v`. All 15 currently pass. |
| 5 | Can they compare outputs to known-good examples? | Yes -- this is the heart of validating a *simulated* dataset. See "Parameter Sourcing" below: every distribution parameter is checked against a real, cited industry benchmark, and `tests/test_stadium_concessions.py` enforces the resulting bounds automatically on every run. |
| 6 | Can they restore from backup? | Yes. `RANDOM_SEED = 42` in the script means the exact same season is regenerated byte-for-byte every time it's run -- "restore" is just re-running `python stadium_concessions.py`. |
| 7 | Can they update dependencies safely? | Yes. Two dependencies (`numpy`, `pytest`), version-pinned in `requirements.txt`. Run the test suite after any upgrade -- if all 15 tests still pass, the upgrade is safe. |
| 8 | Can they explain the business value? | Yes. See `README.md` section 1 -- explains why proprietary POS data makes direct measurement impossible, and how a defensibly-parameterized proxy model answers the same ROI question anyway. |

## Parameter Sourcing (the "known-good examples" this simulation is checked against)

| Model parameter | Value used | Real-world benchmark it's checked against |
|---|---|---|
| Home games per season | 81 | Every MLB team plays exactly 81 home games -- not an assumption, a rule. |
| Number of Bark in the Park nights | 5 | Matches the Detroit Tigers' actual 2026 promotional calendar, which lists exactly five Bark in the Park dates. |
| Season-average attendance | ~27,000-28,000 (simulated) | MLB's published 2025 league-average attendance was just over 29,000/game; this model represents a mid-market franchise, so a modest discount from the league average is expected and realistic. |
| Stadium capacity | 38,000 | A round number representative of a mid-market MLB ballpark (real capacities range from ~30,000 to ~56,000 across the league). |
| Revenue per capita (blended) | ~$22-24 standard nights, ~$30-35 promo nights | Falls inside the range implied by published fan-spending research, which puts total per-attendee food/drink spend from the high teens (lowest-spending fan bases) to over $130 (highest, self-reported, likely includes buying for a group) -- this model's figures sit deliberately in the conservative-but-realistic middle of that range, appropriate for a POS-style per-cap number rather than a self-reported survey number. |

## Automated Realism Checks

`tests/test_stadium_concessions.py` doesn't just check that the code runs
without crashing -- it actively asserts the *simulated distribution*
stays inside these realistic bounds every time the season is generated:

- No single game's attendance ever exceeds stadium capacity or falls below zero.
- Season-average attendance lands between 20,000 and 36,000 (a wide but
  real band around the MLB league average).
- Every game's revenue per capita falls between $5 and $75.
- Promo nights draw more fans, on average, than standard nights.
- The **specialty** item per-cap lift on promo nights is larger than the
  **standard** item per-cap lift -- this is the model's central thesis,
  and the test suite confirms it's actually true in the generated data,
  not just assumed.
- Every Bark in the Park night is net-profitable after its extra cleaning cost.

## Manual Spot-Check (in addition to automated tests)

1. Open `stadium_concessions.db` and look at the 5 rows where
   `is_promo_night = 1`. Confirm their dates are spread across different
   months (not clustered in one week) and mostly fall on weekdays --
   both match how real MLB teams actually schedule these promotions (see
   the Detroit Tigers' 2026 Bark in the Park schedule, cited above, for a
   real example of this exact pattern).
2. Run `analysis.sql`'s Query 2 (the revenue mix query) and confirm the
   specialty item's share of total revenue is meaningfully higher on
   promo nights than standard nights -- if it isn't, something is wrong
   with the `SPECIALTY_PERCAP_PROMO` parameter at the top of
   `stadium_concessions.py`.
3. Change `RANDOM_SEED` to a different number, re-run the script, and
   confirm the season "looks different" (different exact numbers) but
   the same qualitative story holds -- promo nights still draw more fans
   and post a higher revenue per cap. If a single new seed reverses the
   entire conclusion, the model's variance parameters are too wide and
   should be tightened.
